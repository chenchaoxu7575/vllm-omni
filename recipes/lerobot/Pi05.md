# Pi0.5 (π0.5) VLA

> Vision-Language-Action policy serving over the OpenPI realtime websocket

## Summary

- Vendor: Physical Intelligence (checkpoint redistributed by LeRobot)
- Model: `lerobot/pi05_base`
- Task: Vision-Language-Action — multi-camera images + a language instruction +
  robot proprioceptive state → a continuous action chunk
  `[action_horizon, action_dim] = [50, 32]` via flow-matching denoising. π0.5
  does **not** emit text tokens.
- Mode: Online serving via the OpenPI realtime robot API
  (`/v1/realtime/robot/openpi` websocket)
- Maintainer: Community

## When to use this recipe

Use this recipe to deploy `lerobot/pi05_base` as a robot policy server: a robot
client connects over the OpenPI websocket and, per control step, sends an
observation (camera frames + state + instruction) and receives an action chunk.

A single pipeline class (`Pi05Pipeline`) serves the policy. π0.5 is stateless
across calls (first-order Markov, no KV reuse), so the protocol's `session_id` /
`reset` are accepted but ignored.

## How π0.5 differs from π0

Both are PaliGemma (SigLIP + Gemma-2B) + a Gemma-300M action expert + a
flow-matching head. π0.5 changes five things, and two of them change what a
*correct* action chunk looks like without changing any tensor shape:

| | π0 | π0.5 |
|---|---|---|
| Timestep conditioning | `action_time_mlp_*`, time concatenated onto the action embedding | `time_mlp_*` driving **AdaRMS** |
| AdaRMS | not used | used in every action-expert norm |
| Tokenizer length | 48 | **200** |
| State input | continuous, via `state_proj` | **discretized into prompt tokens** |
| Default normalization | `MEAN_STD` | **`QUANTILES`** (`q01`/`q99`) |

The state is normalized to `[-1, 1]`, discretized into 256 bins, and serialized
into the prompt as `Task: <instruction>, State: <b0> ... <b31>;\nAction: `. The
model therefore receives **no state tensor** — only images and language tokens.

## Scope of this deployment

This is the functional path. It carries **no CUDA Graph capture, no Triton
kernels and no prefix/encoder caching**; those are tracked separately.

Two π0.5 capabilities are deliberately **not** supported, and a checkpoint that
declares them is rejected at load time rather than served incorrectly:

- **MEM** short-horizon observation memory (`use_visual_memory`,
  `use_proprioceptive_memory`) — needs a per-session observation history, which
  this stateless serving path does not keep.
- **RTC** real-time chunking (`rtc_config`) — needs prefix guidance inside the
  denoising loop and per-request carry-over of the previous chunk.

`rtc_training_max_delay > 0` is *not* rejected: it describes how the checkpoint
was trained, not a request to run RTC at inference.

**Relative actions are supported** (`use_relative_actions`). This matters for
correctness, not just features: when a checkpoint is trained with relative
actions, its `norm_stats` are computed in *relative* space. Serving it without
the transform unnormalizes a relative-space distribution as if it were absolute,
which produces plausible-looking wrong actions that are invisible in the weights.
The pipeline honours the checkpoint's setting even if the deploy yaml is silent,
and logs a warning when it does.

When `use_relative_actions` is on, the checkpoint's `config.json` must also carry
`action_feature_names` (LeRobot fills it from dataset metadata at training time).
Without it, `relative_exclude_joints: [gripper]` cannot be resolved to an action
index, and the server refuses to start rather than silently making the gripper
relative.

## Weights

π0.5 uses the LeRobot `lerobot/pi05_base` checkpoint. Either let the server
download it (`MODEL=lerobot/pi05_base`) or point at a local copy.

### 1x <GPU> <memory> (Online serving)

#### Environment

- OS: Ubuntu 22.04+
- Python: 3.12+
- Driver / runtime: NVIDIA CUDA environment
- vLLM / vLLM-Omni: use the commit you are deploying from
- OpenPI client extras (for the example client): `openpi-client`
  (`pip install -e packages/openpi-client` from the
  [openpi](https://github.com/Physical-Intelligence/openpi) repo), `websockets`,
  `msgpack`, `msgpack-numpy`

#### Command

```bash
vllm serve lerobot/pi05_base \
  --omni \
  --host 0.0.0.0 --port 8000 \
  --served-model-name pi05 \
  --deploy-config vllm_omni/deploy/pi05.yaml \
  --enforce-eager --disable-log-stats
```

The deploy config (`vllm_omni/deploy/pi05.yaml`) declares a single diffusion
stage (`Pi05Pipeline`), `float32`, `max_num_seqs: 1`, `tokenizer_max_length: 200`,
`state_num_bins: 256`, and the `policy_server_config` handshake metadata.

#### Verification

The observation is a flat dict per inference:

```python
{
    "observation.images.base_0_rgb":        np.uint8[H, W, 3],
    "observation.images.left_wrist_0_rgb":  np.uint8[H, W, 3],
    "observation.images.right_wrist_0_rgb": np.uint8[H, W, 3],
    "state":   np.float32[state_dim],   # zero-padded to max_state_dim=32 server-side
    "prompt":  "pick up the red block",
    "session_id": "<uuid>",             # accepted but ignored (π0.5 is stateless)
}
```

Camera keys must match the server's `image_feature_keys` (the checkpoint's
`input_features` order). If your robot uses different camera names, set
`model_config.image_key_map` in `pi05.yaml`.

Prefix token layout, useful for latency accounting:

```
prefix = 256 tokens/view x (1..3 views)  +  200 text tokens   ->  max 968
```

The text segment is always padded to exactly 200 tokens, so the tensor shape is
constant and only `attention_mask.sum()` varies per request.

## Correctness

The flow-matching kernel is checked against the LeRobot `PI05Policy` reference
under fixed noise, covering 1/2/3 views, the discretized-state prompt tokens, and
both `use_relative_actions=False` and `True`:
`tests/diffusion/models/pi05/test_pi05_parity.py`.

CPU unit tests that need no weights and no lerobot:
`tests/diffusion/models/pi05/test_pi05_units.py`.
