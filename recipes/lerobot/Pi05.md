# Pi0.5 (π0.5) VLA

> Vision-Language-Action policy serving over the OpenPI realtime websocket

## Summary

- Vendor: Physical Intelligence (checkpoint redistributed by LeRobot)
- Model: `lerobot/pi05_base`
- Task: Vision-Language-Action — multi-camera images + a language instruction +
  robot proprioceptive state → a continuous action chunk
  `[action_horizon, action_dim] = [50, 32]` via flow-matching denoising. π0.5
  does **not** emit text tokens.
- Mode: Online serving via the OpenPI realtime robot API
  (`/v1/realtime/robot/openpi` websocket)
- Maintainer: Community

## When to use this recipe

Use this recipe to deploy `lerobot/pi05_base` as a robot policy server: a robot
client connects over the OpenPI websocket and, per control step, sends an
observation (camera frames + state + instruction) and receives an action chunk.

A single pipeline class (`Pi05Pipeline`) serves the policy. π0.5 is stateless
across calls (first-order Markov, no KV reuse), so the protocol's `session_id` /
`reset` are accepted but ignored.

## How π0.5 differs from π0

Both are PaliGemma (SigLIP + Gemma-2B) + a Gemma-300M action expert + a
flow-matching head. π0.5 changes five things, and two of them change what a
*correct* action chunk looks like without changing any tensor shape:

| | π0 | π0.5 |
| --- | --- | --- |
| Timestep conditioning | `action_time_mlp_*`, time concatenated onto the action embedding | `time_mlp_*` driving **AdaRMS** |
| AdaRMS | not used | used in every action-expert norm |
| Tokenizer length | 48 | **200** |
| State input | continuous, via `state_proj` | **discretized into prompt tokens** |
| Default normalization | `MEAN_STD` | **`QUANTILES`** (`q01`/`q99`) |

The state is normalized to `[-1, 1]`, discretized into 256 bins, and serialized
into the prompt as `Task: <instruction>, State: <b0> ... <b31>;\nAction:`. The
model therefore receives **no state tensor** — only images and language tokens.

## Scope of this deployment

This is the functional path. It carries **no CUDA Graph capture, no Triton
kernels and no prefix/encoder caching**; those are tracked separately.

Two π0.5 capabilities are deliberately **not** supported, and a checkpoint that
declares them is rejected at load time rather than served incorrectly:

- **MEM** short-horizon observation memory (`use_visual_memory`,
  `use_proprioceptive_memory`) — needs a per-session observation history, which
  this stateless serving path does not keep.
- **RTC** real-time chunking (`rtc_config`) — needs prefix guidance inside the
  denoising loop and per-request carry-over of the previous chunk.

`rtc_training_max_delay > 0` is *not* rejected: it describes how the checkpoint
was trained, not a request to run RTC at inference.

**Relative actions are supported** (`use_relative_actions`). This matters for
correctness, not just features: when a checkpoint is trained with relative
actions, its `norm_stats` are computed in *relative* space. Serving it without
the transform unnormalizes a relative-space distribution as if it were absolute,
which produces plausible-looking wrong actions that are invisible in the weights.
The pipeline honours the checkpoint's setting even if the deploy yaml is silent,
and logs a warning when it does.

When `use_relative_actions` is on, the checkpoint's `config.json` must also carry
`action_feature_names` (LeRobot fills it from dataset metadata at training time).
Without it, `relative_exclude_joints: [gripper]` cannot be resolved to an action
index, and the server refuses to start rather than silently making the gripper
relative.

## Weights

π0.5 uses the LeRobot `lerobot/pi05_base` checkpoint (~14.5 GB, float32). Either
let the server download it (`MODEL=lerobot/pi05_base`) or point at a local copy.

The PaliGemma tokenizer comes from `google/paligemma-3b-pt-224`, which is a
**gated** repository, and the π0.5 checkpoint ships no tokenizer of its own.
Accept the license on Hugging Face and `hf auth login` before first run, or the
server fails to start with a 401 during model load.

Normalization statistics are read from the checkpoint automatically. LeRobot
keeps them out of `config.json`: `policy_preprocessor.json` holds the pipeline
structure and a companion `policy_preprocessor_step_*.safetensors` holds the
numbers, and both are honored here, with the mode (`mean_std` / `min_max` /
π0.5's default `quantile`) taken from the sidecar's `norm_map`. A `norm_stats`
block in `config.json` or in the deploy yaml overrides the sidecar.
`lerobot/pi05_base` declares no stats at all, i.e. identity normalization: the
state passes through and the client is expected to send an already-normalized
one. A normalization mode this implementation cannot reproduce raises at load
time rather than being served with the wrong transform.

## Hardware Support

Verified functionally on three architectures with the same code and the same
`pi05.yaml`. Peak memory is the serving path at `max_num_seqs: 1`.

| GPU | Arch | Serving peak | Notes |
| --- | --- | --- | --- |
| RTX 4090 24 GB | sm_89 | 14.7 GiB of 22.5 GiB | Tightest supported configuration |
| H100 80 GB HBM3 | sm_90 | 15.7 GiB | |
| RTX PRO 5000 72 GB | sm_120 | 15.7 GiB | |

Those figures are float32. A 24 GB card is enough there, with no meaningful
headroom below that since the weights alone are 14.5 GB. The maintained
full-model regression target is one H100, matching the hardware used for
subsequent optimization work.

### 1x GPU >= 24 GB (Online serving)

#### Environment

- OS: Ubuntu 22.04+
- Python: 3.12+
- Driver / runtime: NVIDIA CUDA environment
- vLLM / vLLM-Omni: use the commit you are deploying from
- OpenPI client extras (robot side, and for the e2e test): `openpi-client`,
  `websockets`, `msgpack`, `msgpack-numpy`. CI pins `openpi-client` to OpenPI
  revision `215abfb217dbac7d5f1273282331b9b1866c0479`.

#### Command

```bash
vllm serve lerobot/pi05_base \
  --omni \
  --host 0.0.0.0 --port 8000 \
  --served-model-name pi05 \
  --deploy-config vllm_omni/deploy/pi05.yaml \
  --enforce-eager --disable-log-stats
```

The deploy config (`vllm_omni/deploy/pi05.yaml`) declares a single diffusion
stage (`Pi05Pipeline`), `float32`, `max_num_seqs: 1`, `tokenizer_max_length: 200`,
`state_num_bins: 256`, and the `policy_server_config` handshake metadata.

The keys under `stages[0].model_config` that are most often adjusted:

| Key | Default | Meaning |
| --- | --- | --- |
| `chunk_size` | `50` | Action-chunk length (timesteps) predicted per inference. |
| `n_action_steps` | `50` | Must equal `chunk_size`; partial client-side action queues are not implemented by the stateless server. |
| `num_inference_steps` | `10` | Flow-matching Euler denoising steps. |
| `max_action_dim` | `32` | Action dimensionality (actions are padded to this). |
| `max_state_dim` | `32` | State dimensionality (zero-padded to this). |
| `image_resolution` | `[224, 224]` | Per-camera input size (square; SigLIP). |
| `tokenizer_max_length` | `200` | Max prompt tokens; π0 uses 48 because it does not carry the state here. |
| `state_num_bins` | `256` | Bins the normalized state is discretized into. |
| `max_cameras` | `3` | Camera slots attended to (real + `-1`-padded). |
| `image_feature_keys` | 3 `observation.images.*` keys | Camera order the model attends to. |
| `image_key_map` | `{}` | Map raw obs camera keys onto `image_feature_keys` (empty = verbatim). |
| `use_relative_actions` | `false` | Predict actions relative to the current state. Leave false unless the checkpoint was trained that way. |
| `relative_exclude_joints` | `["gripper"]` | Action names kept absolute when relative actions are on. |

Keep `policy_server_config`'s `action_horizon` / `action_dim` /
`image_resolution` in sync with the values above. Startup rejects inconsistent
metadata, and the online-serving test checks the advertised handshake.

#### Verification

The observation is a flat dict per inference:

```python
{
    "observation.images.base_0_rgb":        np.uint8[H, W, 3],  # or float32 in [0, 1]
    "observation.images.left_wrist_0_rgb":  np.uint8[H, W, 3],
    "observation.images.right_wrist_0_rgb": np.uint8[H, W, 3],
    "state":   np.float32[state_dim],   # zero-padded to max_state_dim=32 server-side
    "prompt":  "pick up the red block",
    "session_id": "<uuid>",             # accepted but ignored (π0.5 is stateless)
    "sampling_params": {"num_inference_steps": 4},   # optional engine knobs
}
```

Camera keys must match the server's `image_feature_keys` (the checkpoint's
`input_features` order). If your robot uses different camera names, set
`model_config.image_key_map` in `pi05.yaml`. At least one configured camera and
a non-null state are required. Present cameras are compacted in checkpoint
order and empty graph slots are appended only at the tail.

PIL and uint8 images use the `[0, 255]` domain. Floating ndarray/tensor images
must be finite and in `[0, 1]`; they are always converted with `x * 2 - 1`.

`sampling_params` carries engine knobs, kept out of the observation itself
because every other key there is a robot-defined feature name. It currently
holds one: `num_inference_steps`, a positive integer that overrides the
deploy-config denoising steps for this request, trading accuracy for latency.

A name the namespace does not define is rejected rather than ignored, so a
misspelling cannot leave the request silently running on the default.

Prefix token layout, useful for latency accounting:

```text
prefix = 256 tokens/view x (1..3 views)  +  200 text tokens   ->  max 968
```

The text segment is always padded to exactly 200 tokens, so the tensor shape is
constant and only `attention_mask.sum()` varies per request.

## Choosing a dtype

`float32` and `bfloat16` are both supported; `dtype` in the deploy config
selects between them. They are not interchangeable, so pick deliberately.

**float32 is the default and the dtype the correctness evidence covers.**
`lerobot/pi05_base` is stored in float32 and the LeRobot parity oracle runs in
float32, where action chunks match bit-for-bit.

**bfloat16 halves resident weights and is substantially faster.** Measured on
one RTX PRO 5000 72 GB, 10 denoising steps, same weights and same fixed noise:

| views | bs | float32 p50 | bfloat16 p50 | Speedup | float32 peak | bfloat16 peak |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 1 | 187.2 ms | 146.0 ms | 1.28x | 13.65 GB | 6.84 GB |
| 3 | 1 | 283.7 ms | 168.8 ms | 1.68x | 13.79 GB | 6.92 GB |
| 3 | 2 | 439.9 ms | 204.0 ms | 2.16x | 14.07 GB | 7.06 GB |

The cost is numerical. Against the same float32 run, bfloat16 action chunks
deviate by up to `4.6e-2` (mean `6.6e-3`, ~1-2% of the action range) at 3 views.
Three properties of that deviation matter more than its size:

- **It is systematic, not noise.** Repeating either dtype reproduces its own
  output exactly, so the gap does not average out across control steps.
- **It compounds through the denoising ODE**, growing roughly 12-20x from the
  first Euler step to the tenth.
- **Near-zero action dimensions can flip sign**, which reverses the commanded
  direction on those joints.

Whether that is acceptable is a property of the robot and the task, and
answering it needs rollout or task-success evidence rather than tensor
comparison. Validate bfloat16 on your own task before deploying it; use float32
when you need the behaviour the parity tests pin down.

`float16` is rejected at startup. It is not a supported serving dtype here and
has not been validated.

## Correctness

The flow-matching kernel is checked against the LeRobot `PI05Policy` reference
under fixed noise, covering 1/2/3 views, the discretized-state prompt tokens, and
both `use_relative_actions=False` and `True`:
`tests/diffusion/models/pi05/test_pi05_parity.py`.

CPU unit tests that need no weights and no lerobot:
`tests/diffusion/models/pi05/test_pi05_units.py`.

An online-serving end-to-end test drives the real OpenPI websocket against a
live server — handshake metadata, observation, action chunk:
`tests/e2e/online_serving/test_pi05_expansion.py`. It needs `openpi-client`,
`websockets`, `msgpack` and `msgpack-numpy`; the explicit nightly H100 job fails
if those dependencies are unavailable.
